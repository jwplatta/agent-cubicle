# Execution graph, events and PostgreSQL: draft contract

Status: design, 2026-11-01. No application schema or orchestration implementation has been applied. Companion to [supervisor plan](supervisor-orchestration.md). Start with one adapter while supporting two concurrent workstreams; this contract is a candidate to validate, not a commitment to build every table immediately.

## Initialization and process model

Proposed `cubicle init` idempotently creates `~/.cubicle/config.yaml`, a central `~/.cubicle/backlog/`, and `~/.cubicle/context/`, `~/.cubicle/logs/`, `~/.cubicle/runs/`, and `~/.cubicle/artifacts/` for working context, logs and artifacts. It must preserve existing settings, environment and backlog, and report what was created. Temporary files must not be the only copy of a prompt, event or artifact needed for audit or recovery. Store durable outputs in PostgreSQL or a configured durable artifacts directory. Existing `~/.cubicle/.env` remains the shared environment source initially; avoid introducing a second secret file without a reason. Config YAML holds non-secret settings, e.g. backend selection, DB host/name, per-provider usage thresholds, timeouts and tool policy. Inherited environment overrides local configuration when explicitly documented; read secrets from environment or a local restricted-permission env file, without printing them. Do not place credentials in the repo or database event payloads.

Proposed `cubicle supervisor` starts an interactive Codex supervisor by default; a config value and e.g. `--backend claude` override select another adapter. Establish how the selected CLI loads the Cubicle supervisor skill and interactive session, and how it calls durable Cubicle operations, before implementation. CLI supervisor is not itself the daemon: the worker manager must persist/reattach independently enough for a closed terminal not to falsely mark work finished. Avoid assuming that execvpe by itself provides monitoring.

## What is a node?

The supervisor decomposes a task into explicitly created, reviewable bounded nodes and assigns each node to a worker. A node is a work package: one objective, a bounded set of inputs and allowed scope, expected output, checks, dependencies, execution limits and an assigned worker policy. It ends when a worker returns, is stopped/fails, or reaches a specified bound; a gate evaluates its saved result separately. A node can contain many tool calls, shell commands and provider subagents. Those are observations inside its run, not automatically new Cubicle graph nodes. The supervisor creates and revises nodes when decomposition or a dependent step warrants it; a worker may suggest a graph change but does not independently redefine the supervisor’s graph; initially a graph may consist of a single node. Prefer a continuing worker session for the entire backlog task: after each node result the supervisor evaluates evidence and assigns the next node or requests a correction in the same session. A worker can make many model and tool calls inside each node; deliberate parallelism can add sessions. A graph version snapshots nodes and directed dependencies so later edits do not rewrite history. Versioned graph records and an append-only decision event make changes inspectable. Avoid cycles in dependency edges; retry is a new attempt, not a cyclic edge. A correction records its failed check and originating attempt.

Example: Task = repair a bug, obtain review, merge its PR and clean up the local branch. The supervisor creates nodes to reproduce the bug, implement the fix, run relevant checks, and prepare the PR, with explicit dependencies and bounded inputs/outputs. Independent work may run in parallel only when scopes do not conflict; the supervisor owns integration and acceptance. For review feedback, identify the affected node using evidence, create a linked correction attempt, rerun its gate and affected downstream checks, and update the PR. Do not mark the coding task complete until the PR merge and safe local branch cleanup are verified; user review/authorization governs merging. A non-coding task requires explicit user confirmation of completion. Each node records ID, task/graph IDs, kind, objective, input references and pinned revisions, allowed paths/actions, output requirements, checks, model/backend selection or policy, deadline/limits, state and timestamps. Start small; not every field needs its own table.

## IDs, sessions and attribution

A backlog item, task, graph/version, node, Cubicle worker session and node assignment/run each have separate IDs. A task links to its backlog item; each session links to its task and backend plus provider session/conversation ID. Each node assignment is a new run linked to both the node and worker session; retries and corrections link to their predecessor. The supervisor records the handoff and its outcome before moving to the next node. Resume uses the provider's session identifier where supported; capture failure and link any replacement session to its predecessor.

Reuse creates an attribution challenge: a run ID injected only when a long-lived CLI starts can become stale. For the initial Codex adapter, prototype a separate exec/resume process per node assignment, passing a non-secret run marker and recording the provider session ID; SessionStart tests observed the correct marker for both startup and resume. Do not assume agent shell commands inherit the marker: the local shell environment allowlist filtered it. Validate per-turn correlation, other hook types, session-to-active-run mapping, asynchronous subagents and late events for each adapter. Use provider turn/tool IDs or a verified per-assignment mechanism where available. Do not infer a node merely from an event timestamp when runs overlap; keep uncertain events linked to the session with node attribution unknown.

## Event ingestion: no agent bookkeeping required

Three producers deliver to a common ingestion function with a stable run ID: (1) Cubicle manager records dispatch, process lifecycle, cancellation, errors and result; (2) adapters parse JSONL stdout/stderr as provided by each CLI; (3) provider hooks send native events and payloads, including tool and subagent lifecycle when emitted. Native workers call the same ingestion interface. The worker reports its decisions, output, checks and evidence for its assigned node; it is not responsible for logging every operational action. Operational events are stored separately from graph state and linked to the appropriate run/node where correlation is reliable. A wrapper supplies a destination and correlation context to child processes and hooks; prototype whether each provider actually preserves these variables, including subagents. Pass run ID and endpoint/spool path, not database credentials, if a local collector is used.

For the first host-only design, use a run-specific durable spool and wrapper that survives the manager; ingest into PostgreSQL with stable IDs and transactional acknowledgments. Use a concurrency-safe framing strategy for hook callbacks and preserve required hook stdout. Validate this choice under failure before implementation is considered reliable. A spool must use atomic/concurrency-safe writes, bounded storage and replay with a stable event ID; cleanup must not erase un-ingested evidence. Report a telemetry gap and fallback error to stderr/local durable log when ingestion fails. Never swallow an error; avoid recursive logging failures. Explicitly decide what happens if policy checks fail; observation hooks need not block the agent. Do not insert raw secrets. stdout event stream and hook observations can overlap: retain provenance and avoid double-counting; no reliable provider event ID means correlation and deduplication are best-effort.

Normalized envelope: event_id, schema_version, observed_at and ingested_at, source (manager/stream/hook/native), backend, event_type and native_type, task_id/node_id/run_id and Cubicle worker_session_id if known, provider session/subagent/tool call IDs if available, source sequence, payload JSON and optional raw payload reference. Keep unknown IDs nullable and link later only on evidence. Events may arrive out of order. Source-level occurrence and ingestion time are distinct. Examples: run.started, run.finished, tool.started, tool.finished, subagent.started, subagent.finished, hook.failed, usage.reported and artifact.created. Payloads need size, redaction and retention policies, not assumed unlimited raw logs.

Shell calls are typically visible as a CLI tool call with command and result where the provider exposes them. Processes started *inside* that shell and their full internal behavior are not necessarily observable. Provider subagents are associated by native session/subagent IDs where supplied; do not pretend all have explicit graph nodes or that the hook captured their every tool. Claude documents SubagentStart/Stop; the installed CLI exposes `--include-hook-events`. Codex JSONL documents command and tool items. agy's installed CLI exposes stream-json and hooks but exact payload/child propagation needs a live test. Capture nested activity only when supported; mark gaps. [Codex event examples](https://developers.openai.com/codex/noninteractive/), [Claude hook events](https://code.claude.com/docs/en/hooks), [agy hooks](https://codelabs.developers.google.com/genai-for-dev-antigravity-cli).

## Cubicle MCP, skill and deployed prompts

Expose backlog and graph operations through one local Cubicle MCP interface backed by ordinary Python services also callable from the CLI. The supervisor uses it to inspect backlog, define/revise graph nodes and edges, dispatch work, inspect evidence, and accept or return a node. Workers receive a node-scoped contract and can report progress, decisions, artifacts, checks and blockers against that assigned node. Any start/update/end operations describe the lifecycle of that supervisor-defined node; they do not ask the worker to construct the task graph. Capture operational events independently through manager, CLI streams and hooks. Provide a Cubicle skill describing the contract and graph/evidence review utilities; its install and compatibility with each CLI need validation.

Prompts and Cubicle-owned skills are authored and versioned in the Cubicle repository. Installation or `cubicle init` deploys them under `~/.cubicle/` with a manifest recording source revision and content hashes; preserve enough prior deployed versions or immutable snapshots to interpret historical runs, including dirty-source content. Record the deployed manifest and rendered node prompt/reference per run. Initialization and updates must preserve user configuration and not silently overwrite local changes; exact update policy remains to be designed.

## Example: one task across the CLI adapters

Supervisor task: fix a parser bug and open a PR. The supervisor defines node A to reproduce the bug (report and check), node B to implement the fix (bounded diff; depends on A), node C to verify it (test evidence; depends on B), and node D to prepare a PR (depends on accepted checks), followed by user review, authorized merge and verified safe branch cleanup. Nodes may run on different worker backends; a task can use only one. The supervisor manages at least two concurrently active workstreams with separate task graphs and sessions, for example across two repositories. A failed check returns the relevant node for a bounded new attempt. PR review feedback records its source, identifies an affected node from evidence, and triggers a linked correction plus necessary downstream checks.

- **Codex:** start a worker for a node with `codex exec --json`; map thread ID and JSONL command/file/tool events and turn usage to that run, supplement with supported hooks. Codex app-server demonstrated active `turn/steer` and interruption in a local probe; live steering remains optional for the initial version. Do not assume `exec` itself offers app-server live steering.
- **Claude:** run `claude -p --output-format stream-json --verbose`, optionally `--include-hook-events`; correlate session and available tool/subagent hooks with the run. Resume by explicit session ID when appropriate. Hook lifecycle stream coverage has documented exceptions.
- **agy:** use `agy -p --output-format stream-json`; capture conversation ID, step updates and token usage, plus supported hooks. For streaming input, documentation instructs the caller to wait for a result before supplying the next turn; do not claim in-flight steering. Session results can be cumulative.

For each adapter, test node-scoped environment/session IDs, hook and MCP availability in nested agents, prompts, failure, cancellation, resume and event-to-run attribution with one safe example. An unobservable shell child or ambiguous event remains unknown. The graph is authored by the supervisor; the CLI trajectory is supporting evidence, not automatically promoted to graph nodes.

## Candidate relational schema

Use UUID primary keys, timestamptz and JSONB for evolving provider-specific metadata; make foreign keys and indexes explicit. Table names are tentative. The minimum pilot needs tasks, nodes, runs and events; add the others only as the relevant capability is exercised.

| Table | Key fields and role |
| --- | --- |
| tasks | id, backlog_ref, title, objective, constraints JSONB, acceptance JSONB, status, completion_kind, user_confirmation nullable, created_at, updated_at; coding completion requires merged PR and safe cleanup; non-coding completion requires explicit user confirmation |
| graphs | id, task_id FK, version, created_at, status; unique(task_id, version) |
| nodes | id, graph_id FK, logical_key, kind, objective, inputs JSONB, scope JSONB, outputs JSONB, checks JSONB, limits JSONB, worker_spec JSONB, status, timestamps; unique(graph_id, logical_key) |
| node_edges | graph_id, from_node_id, to_node_id, condition/check reference; unique pair per graph; validate same-graph references and acyclic dependencies in transaction |
| worker_sessions | id, task_id FK, backend, provider_session_id nullable, predecessor_session_id nullable, status, created_at, ended_at; provider IDs are scoped by backend |
| runs | id, node_id FK, worker_session_id FK, parent_run_id nullable, retry_of_run_id nullable, backend, model nullable, process/turn references, context_manifest JSONB, status, start/end, exit_code, result JSONB; indexes on node and session |
| events | event_id PK, run_id FK nullable, source, native_type, type, occurred_at, ingested_at, source_sequence nullable, session_id/subagent_id/tool_call_id nullable, payload JSONB, raw_ref nullable; index (run_id, ingested_at, event_id), plus session correlation as needed |
| artifacts | id, run_id FK, kind, durable URI/path, content hash, base revision, metadata JSONB, created_at; include PR URL/identity, merge evidence, cleanup evidence and diff/check references |
| evaluations | id, run_id FK, node/check reference, evaluator, verdict, score nullable, evidence/artifact reference, notes and time; human review recorded separately from automated check |
| usage_observations | id, run_id nullable, provider/account alias, scope (turn/run/session/account), source, observed_at, window/reset, input/output/cached token counts nullable, percent nullable, raw_ref nullable; store units, cumulative vs delta, provenance and unknowns |

Backlog Markdown remains the task source for planning; PostgreSQL records execution and a reference/snapshot so changes are auditable. Do not mirror edits bidirectionally without a conflict policy. Run and state transitions should be transactional; event ingestion uses idempotency keys, parameterized writes and per-run indexes. Do not use an identity/sequence value or timestamp alone as a commit-order high-water cursor: concurrent transactions may commit out of allocation order. Use transactional acknowledgments and replayable unacknowledged spool entries; test concurrent commits and crash recovery. Database backup, retention, migrations, concurrent connections, credentials and access control require explicit implementation decisions.

## Token usage, permissions and configuration

[Codex exec JSON](https://developers.openai.com/codex/noninteractive/) documents turn-completed usage including input, cached input and output tokens. [Claude programmatic output](https://code.claude.com/docs/en/headless) includes usage metadata and estimated cost; resumed-session cost can be cumulative and does not establish subscription spending. Capture supplied raw values, scope and provenance; do not sum cumulative totals as independent runs. [agy headless documentation](https://antigravity.google/docs/cli/headless/) describes per-step and result token usage, with cumulative session totals in multi-turn streaming mode; validate installed-version and nested-agent behavior before relying on it. Account-window percentages and individual task tokens are different measures.

The user wants unattended host workers with permission bypass. Installed help lists Codex `--dangerously-bypass-approvals-and-sandbox`, Claude `--dangerously-skip-permissions`, and agy `--dangerously-skip-permissions`; exact effects vary, and Codex's flag also disables its sandbox. Host mode grants broad access; task scope in a prompt and a common allowlist are not enforcement. Claude advertises tool allow/deny options, while comparable controls and how they interact with bypass mode must be verified independently for each backend. Shell access can bypass simple tool-name restrictions. Design a common intent/policy model plus per-adapter capabilities; report unenforceable rules instead of claiming equivalence. Use isolated worktrees for coding where appropriate and retain explicit human review of PRs. Configurable usage thresholds and timeouts apply per provider/account where measurable; do not assume cancellation can reverse external side effects.

## Control and recovery test findings

Local probes observed Codex app-server accept live steering and report an interrupted turn; temporary Codex and Claude hooks captured a parent marker and child-agent ID through one nested tool flow. agy exposed a subagent invocation in its stream but child hook coverage remains unverified. Two detached Codex workers finished into separate files after a throwaway manager was killed, but no Cubicle restart or durable PostgreSQL reconciliation was tested. See [CLI experiments](../notes/cli-worker-research.md) for methods and limitations. Treat these as feasibility evidence, and require end-to-end restart, cancellation, concurrent attribution and orphan-cleanup tests for the actual manager.

## Initial control and recovery decisions

Use one CLI process per node assignment and resume the same provider session across sequential assignments when supported. Persist a unique run ID before launch and use a run-specific wrapper and spool; hooks receive a non-secret run marker where tested. Independent workstreams use different sessions. Do not overlap assignments in one session or attribute ambiguous late events by time alone. Graceful cancellation and confirmed or explicitly unknown terminal state are required; live in-flight steering is optional, with node boundaries used for ordinary direction changes. On restart, reconcile durable run records, wrapper identity, terminal markers and spool; never blindly retry an ambiguous side-effecting launch or kill an unverified PID. Full design, PostgreSQL prototype and outstanding acceptance tests: [CLI research](../notes/cli-worker-research.md).
